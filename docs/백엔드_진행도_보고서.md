## 1. 요약

백엔드는 **지도용 공개 API**(격자·인프라·detail·도시행사·제보)와 **인증·관리자 API**가 1차 데모 수준으로 동작한다.  
추가로 `src/jobs` **운영 안전등급 배치**가 구현·실측 반영되어, FE가 읽는 `grid.safety_grade`가 시설·제보 기반으로 채워진 상태다.

남은 과제는:

1. **모델 고도화** — 보행자 사고다발 CSV를 DB 적재 없이 배치 입력으로 반영 (미구현)
2. **정합 버그** — 회원가입 `role: "USER"` vs 스키마 `NORMAL`, FE `"위험"` vs BE `"불안"`(불안으로 진행.)
3. **스키마만 있는 auth** — `refresh_token` 테이블/Prisma 모델은 있으나 refresh API 미구현
   (현제는 구현X.)
4. **문서** — `격자_인프라_진행명세서`에 jobs·FE 최신 상태 반영 부족

한 줄 평가:

> API 골격과 1차 스코어 배치는 완료. 다음은 **모델(사고다발) 개량**, **auth/role 정합**, **FE 색상 키 맞춤**이다.

## 4. 안전등급 모델 (상세)

### 4.1 설계 원칙

| 원칙 | 내용 |
| :--- | :--- |
| 담당 범위 | **`src/jobs/**`만** (controllers/routes/schema/FE 불변 목표) |
| 입력 | DB `infrastructures` + 활성 `report` |
| 출력 | **`grid.safety_grade`만** UPDATE (`안전` / `보통` / `불안`) |
| 숫자 점수 | `safety_baseline`, `event_penalty`, `safety_strength`는 **메모리 전용** (컬럼 없음) |
| 스키마 | 배치를 위한 변경 없음 |
| 출처 | `risk_pipeline/config.py` 공식을 BE `infrastructures.type`에 맞게 이식 |

파일:

| 파일 | 역할 |
| :--- | :--- |
| `src/jobs/weights.ts` | 타입 매핑·가중치·등급 구간 |
| `src/jobs/scoreOps.ts` | 집계 → 점수 → UPDATE |
| `src/jobs/runScore.ts` | CLI (`--dry-run`) |
| `src/jobs/README.md` | 전제·실행법 |

### 4.2 전체 파이프라인

```
┌─────────────────────────────────────────────────────────────┐
│ 1. loadFeatures()                                           │
│    infrastructures groupBy(grid_id, type)                   │
│    + report (is_active=Y, 미만료)                            │
│         ↓                                                   │
│ 2. facilityRaw per source                                   │
│    log1p(weight) + presence_bonus                           │
│         ↓                                                   │
│ 3. z-score (소스별, feature 집합 전체)                       │
│         ↓                                                   │
│ 4. infraScore = Σ SOURCE_WEIGHT[s] * z[s]                   │
│         ↓                                                   │
│ 5. percentile rank → safety_baseline (0~100)                │
│         ↓                                                   │
│ 6. event_penalty = 8 * log1p(report_score)                  │
│    safety_strength = clamp(0,100, baseline − penalty)       │
│         ↓                                                   │
│ 7. strengthToGrade → safety_grade                           │
│         ↓                                                   │
│ 8. applySafetyGrades (dry-run 또는 batch UPDATE 200건)       │
└─────────────────────────────────────────────────────────────┘
```

### 4.3 Step별 설명

#### Step 1 — `loadFeatures()`

1. `infrastructures`를 `(grid_id, type)`로 `groupBy` + count (`grid_id` null 제외).
2. `type` → 시설군 키 매핑 (`INFRA_TYPE_TO_SOURCE`). 매핑 실패 시 skip.
3. 격자별 누적:
   - `{source}_n = count`
   - `{source}_w = count * DEFAULT_POINT_WEIGHT` (= 1.0)
4. `report` 조회 조건:
   - `is_active = 'Y'`
   - `grid_id` not null
   - `expire_at` is null **또는** `expire_at > now`
5. 제보 1건마다 `report_n += 1`, `report_score += REPORT_UNIT_WEIGHT` (= 1.0).

**중요:** 시설도 제보도 없는 격자는 feature 집합에 **포함되지 않음** → 이번 배치에서 `safety_grade`가 **갱신되지 않음**.  
(전체 grid ≈ 67k 중 실측 갱신 **34,003** — 나머진 기존 값 유지.)

#### Step 2 — `facilityRaw` (소스별)

```
raw = log1p(w) + PRESENCE_BONUS[source] × (n > 0 ? 1 : 0)
```

- CCTV·편의점: presence bonus **0** (건수가 곧 신호)
- 경찰서·소방서: **+0.5** (희소 시설 “있다/없다”를 z-score 전에 가산)

`log1p`로 극단적으로 많은 CCTV 격자가 raw를 폭주시키지 않게 완화한다.

#### Step 3 — z-score (소스별)

feature 배열 전체에 대해:

```
μ = mean(raw)
σ = sqrt( Σ(v−μ)² / n )   // 모집단 분산
z = (v−μ) / σ             // σ ≈ 0 이면 전부 0
```

네 소스(cctv/police/fire/conv)를 **각각** 표준화한다.  
같은 “경찰서 1곳”이라도, 전체 격자 분포에서 상대적으로 얼마나 드문지가 z에 반영된다.

#### Step 4 — 인프라 가중합

```
infraScore_i = 0.30·z_cctv + 0.25·z_police + 0.20·z_fire + 0.25·z_conv
```

가중치 합 = 1.0. CCTV 비중을 가장 크게, 소방을 상대적으로 작게 둔다.

#### Step 5 — 백분위 → baseline

`infraScore`에 대해 **평균 순위 백분위**(동점 평균, 1-based / n):

```
safety_baseline = round(pct × 10000) / 100   // 약 0~100
```

해석: “시설 구성이 전체 격자 중 어느 분위인가”를 안전 기반 점수로 쓴다.  
절대 건수가 아니라 **상대 순위**이므로, 데이터셋이 바뀌면 같은 격자라도 baseline이 달라질 수 있다.

#### Step 6 — 제보 패널티 · strength

```
event_penalty = round(8 × log1p(report_score) × 10000) / 10000
safety_strength = clamp(0, 100, round((baseline − event_penalty) × 100) / 100)
```

- 제보 1건: `report_score=1` → `penalty ≈ 8 × ln(2) ≈ 5.55`
- 제보가 많을수록 패널티는 log로 완만히 증가

#### Step 7 — 등급 매핑 (`strengthToGrade`)

| 조건 | `safety_grade` |
| :--- | :--- |
| **활성 제보 1건 이상** OR `strength < 40` | **불안** |
| `40 ≤ strength < 60` | **보통** |
| `strength ≥ 60` | **안전** |

활성 제보가 있으면 strength가 높아도 **무조건 불안**.  
제보 없는 격자만 strength 구간으로 보통/안전을 나눈다.

### 4.4 `weights.ts` 상수표

| 상수 | 값 | 의미 |
| :--- | :--- | :--- |
| `INFRA_TYPE_TO_SOURCE` | CCTV→cctv, 경찰서→police, 소방서→fire, 편의점→conv | DB type 매핑 |
| `SOURCE_WEIGHT` | 0.30 / 0.25 / 0.20 / 0.25 | z 후 가중합 |
| `PRESENCE_BONUS` | police/fire **0.5**, 나머지 0 | 희소 시설 존재 가산 |
| `DEFAULT_POINT_WEIGHT` | 1.0 | 시설 1건당 weight (subtype 없음) |
| `EVENT_PENALTY_SCALE` | 8.0 | 제보 패널티 스케일 |
| `REPORT_UNIT_WEIGHT` | 1.0 | 활성 제보 1건 점수 |
| `GRADE_SAFE_MIN` | 60 | 안전 하한 |
| `GRADE_NORMAL_MIN` | 40 | 보통 하한 (= 불안 상한) |

### 4.6 dry-run vs 실실행

| 모드 | 동작 |
| :--- | :--- |
| `--dry-run` | 전체 계산·등급 집계·최저 strength 샘플 출력, **DB 쓰기 없음** |
| 실실행 | `batchSize=200`으로 `prisma.$transaction` → `grid.safety_grade` UPDATE |

```bash
# backend 루트, .env DATABASE_URL 필요
npx prisma generate
npx ts-node --transpile-only src/jobs/runScore.ts --dry-run
npx ts-node --transpile-only src/jobs/runScore.ts
```

중간 progress 로그는 없음. 실실행은 수만 건 UPDATE라 **수 분** 걸릴 수 있고, 완료 후에야 `grids` / `grades` / `updated` 로그가 나온다.

### 4.7 실측 실행 결과 (2026-07-28)

| 항목 | 값 |
| :--- | ---: |
| 갱신 격자 | **34,003** |
| 안전 | 12,960 |
| 보통 | 8,006 |
| 불안 | 13,037 |

- dry-run과 실실행 **등급 분포 동일**, `updated=34003`으로 DB 반영 확인.
- FE/API는 요청마다 점수를 다시 계산하지 않고 **`grid.safety_grade` 캐시값**을 반환한다.
- 제보·인프라가 바뀌면 **배치를 다시 돌려야** 등급이 갱신된다.

샘플 해석 예:

| grid | strength | grade | reports | 해석 |
| :--- | ---: | :--- | ---: | :--- |
| 2 | 0 | 불안 | 1 | 활성 제보 → 강제 불안 |
| 168 등 | ≈17 | 불안 | 0 | 시설 상대 순위 낮음 → strength&lt;40 |

### 4.8 다음 모델 개량 — 사고다발 CSV (DB 미적재)

**전제:** CSV를 DB에 넣지 않는다. 런타임 API도 CSV를 읽지 않는다.

권장 설계:

```
infrastructures + report (DB)
        +
19_24_pedstrians.csv (배치 실행 시에만 로컬 파일)
        ↓
accident_penalty = SCALE × log1p(사고점수)
strength = baseline − report_penalty − accident_penalty
        ↓
grid.safety_grade UPDATE만
```

| 항목 | 1차 권장 |
| :--- | :--- |
| CLI | `--accidents <csvPath>` (없으면 기존식 100% 유지) |
| 매핑 | CSV `위도/경도` 중심점 → `toRowCol` → `grid_id` |
| 사고점수 | 간단: `사고건수` / 또는 가중: `사망×5+중상×3+…` |
| 폴리곤 | 1차 보류 |
| 스케일 | dry-run으로 `ACCIDENT_PENALTY_SCALE` 튜닝 (예: 4~6) |
| 검증 | 등급 분포 전·후, 불안 비율 급증 여부 |

**현재 코드:** `--accidents` **미구현**. README에도 “본 배치 미사용”.

## 7. 방향성

### 7.1 제품·아키텍처 방향

1. **런타임 = DB + API만** (CSV는 배치/학습 전용)
2. **등급은 캐시 컬럼** — 요청 시 재계산하지 않음
3. **스키마 최소 변경**으로 모델 실험 (점수 컬럼 추가보다 grade UPDATE)
4. **웹 우선** — device/push·앱은 제외/타팀
5. FE는 `safety_grade`만 소비 — 모델 개량해도 FE 계약은 동일

### 7.2 권장 로드맵

| 순위 | 과제 | 이유 |
| :---: | :--- | :--- |
| P0 | `feature/model` → `dev` PR 병합 정리 | jobs·city 필터 공유 |
| P0 | FE `"불안"` 색 매핑 (FE 쪽) / BE 문서에 명시 | 불안 격자 회색 표시 방지 |
| P0 | register `role: "USER"` → `"NORMAL"` | 회원가입 실패 가능 |
| P1 | `--accidents` CSV 배치 입력 + dry-run 튜닝 | 모델 개량 (DB 미적재) |
| P1 | city-events ↔ 관리자 필드 정합 | 진행명세 후속 |
| P2 | auth refresh 구현 **또는** 스키마-only 상태 문서화 | refresh_token 공백 해소 |

## 8. 해결해야 할 점

### 8.1 버그·정합

| 이슈 | 설명 | 조치 |
| :--- | :--- | :--- |
| **FE `위험` vs BE `불안`** | FE `gridStyle`이 `"위험"`만 빨강 매핑 | FE를 `"불안"`으로 수정 (또는 둘 다) |
| **register `role: "USER"`** | 스키마 enum은 `NORMAL`\|`ADMIN` (`auth.controller.ts`) | `"NORMAL"`로 수정 |

## 9. FE·BE 연동 관점

| API / 데이터 | BE | FE | 이슈 |
| :--- | :--- | :--- | :--- |
| `GET /grids` | ✅ | ✅ Polygon | 색상 키 불일치 |
| infrastructures / detail | ✅ | ✅ | — |
| city-events | ✅ + is_active | ✅ 마커·패널 | 필드 정합 점검 |
| reports 조회 | ✅ | ✅ 마커 | 쓰기 UI는 FE 미착수 |
| safety_grade | 배치로 채움 | 캐시 표시 | `"불안"` 매핑 필요 |
| auth | login 등 | login UI | refresh·회원가입 FE 공백 |

BE 배치를 다시 돌려도 **서버 재시작 없이** FE가 다음 `GET /grids`부터 새 등급을 본다 (같은 DB).

## 12. 결론

백엔드는 **공개·관리 API 1차 완성과 운영 스코어 배치 1차 적용**까지 도달했다.  
모델은 “시설 상대 순위로 안전 기반을 만들고, 활성 제보로 불안을 강제·패널티하는” 구조이며, **숫자 점수는 DB에 남지 않고 등급 문자열만** 남긴다.

다음 제품·모델 가치는 **사고다발 CSV를 배치 전용 입력으로 넣어 위험 지역 패널티를 보강**하는 것이고, 이와 병행해 **role/색상/refresh 정합**을 정리해야 FE·데모 품질이 맞는다.
