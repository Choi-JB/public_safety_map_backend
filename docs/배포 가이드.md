# 배포 가이드 (AWS Lightsail + Docker)

## 아키텍처 요약

- **인스턴스**: AWS Lightsail 단일 인스턴스 (Ubuntu)
- 이 인스턴스 안에 **MariaDB(DB)**, **nginx(리버스 프록시 + HTTPS)**, **백엔드 Docker 컨테이너**가 전부 같이 떠 있음
- 백엔드 이미지는 **로컬(Windows)에서 빌드 → Docker Hub에 push → 서버에서 pull**하는 방식 사용 (서버에서 직접 빌드 안 함)
- 프론트엔드는 아직 배포 전, 로컬(`http://localhost:3000`)에서 실행하며 배포된 백엔드에 HTTPS로 접속
- 도메인이 없어서 `nip.io`(무료 wildcard DNS)로 static IP에 도메인처럼 접근: `https://43-202-197-59.nip.io`

```
[로컬 프론트 localhost:3000]
        │  HTTPS 요청
        ▼
[nginx :443, Let's Encrypt 인증서] ── X-Forwarded-Proto 헤더 전달
        │  proxy_pass (내부 HTTP)
        ▼
[Docker 컨테이너: Node/Express, --network host, :5000]
        │
        ▼
[MariaDB :3306, 같은 인스턴스, 127.0.0.1 또는 private IP]
```

## 1. 사전 준비

### 1-1. Lightsail Static IP 고정

Lightsail 콘솔 → 인스턴스 → **Networking** → **Attach static IP**.
(주의: static IP를 새로 붙이면 기존 동적 퍼블릭 IP와 **다른 주소**가 할당될 수 있음. 이후 모든 설정은 이 최종 static IP 기준으로 진행)

### 1-2. Lightsail 방화벽

Networking → Firewall에서 아래 포트 허용:
- `HTTP` (80)
- `HTTPS` (443)
- `3306`은 외부에서 직접 붙을 필요 없으면 막아두는 걸 권장 (같은 인스턴스 안에서는 방화벽과 무관하게 접근 가능)

## 2. Dockerfile

프로젝트 루트의 [Dockerfile](Dockerfile) (멀티스테이지 빌드):

- 1단계(`builder`): `npm ci` → `prisma generate` → `npm run build`(TS 컴파일)
- 2단계(`runner`): 프로덕션 의존성만 설치, masking용 Python venv 구성, `dist`만 복사

**주의사항**
- 반드시 파일명이 정확히 `Dockerfile`이어야 함 (`.Dockerfile`처럼 점 붙이면 Docker가 못 찾음)
- base 이미지는 `node:20-bookworm-slim` (Debian 기반). alpine은 `bcrypt`(네이티브 모듈), `opencv`(masking)와 궁합이 안 좋아서 피함
- masking(`cv2`) 실행을 위해 `libgl1`, `libglib2.0-0`, `python3` 설치 필요
- `EXPOSE`는 `.env`의 `PORT` 값과 일치시켜야 함 (현재 5000)

## 3. Prisma 관련 이슈 (해결됨)

**증상**: 컨테이너 실행 시 아래 에러로 크래시
```
PrismaClientInitializationError: Prisma Client could not locate the Query Engine for runtime "debian-openssl-3.0.x".
```

**원인**: Debian slim 이미지엔 openssl 라이브러리가 기본으로 없어서, 빌드 단계에서 Prisma가 엔진 버전을 잘못 추측함.

**해결**: [prisma/schema.prisma](prisma/schema.prisma)의 generator 블록에 `binaryTargets` 명시
```prisma
generator client {
  provider      = "prisma-client-js"
  binaryTargets = ["native", "debian-openssl-3.0.x"]
}
```

```bash
docker login
```

코드를 수정할 때마다 이 3줄을 다시 실행 → 서버에서 pull 받아 재배포.

## 5. 서버(Lightsail) 환경 구성

### 5-1. Docker 그룹 권한 (선택)

매번 `sudo` 붙이기 싫으면:
```bash
sudo usermod -aG docker $USER
```
적용하려면 SSH 세션 재접속 필요.

### 5-2. `.env` 파일 생성 — 따옴표 없이!

> ⚠️ **중요**: `docker run --env-file`은 `.env`의 `KEY="value"` 형태에서 **따옴표를 벗겨주지 않습니다.** 따옴표를 넣으면 값에 `"`가 그대로 포함되어 `DATABASE_URL` 파싱이 깨지고 DB 연결이 실패합니다 (`pool timeout` 에러로 나타남). 로컬 개발(`dotenv` 사용)에서는 따옴표를 자동으로 벗겨주기 때문에 이 문제가 로컬에서는 안 보였음.

```bash
mkdir -p ~/public_safety_map_backend/uploads
tee ~/public_safety_map_backend/.env > /dev/null <<'EOF'
PORT=5000
DATABASE_URL=mysql://jbong:1234@127.0.0.1:3306/public_safety_map
JWT_SECRET=(실제 값)
SESSION_SECRET=(실제 값)

SCORE_CRON_ENABLED=true
SCORE_CRON_TZ=Asia/Seoul

MASKING_PYTHON=/app/masking/.venv/bin/python

KOROAD_AUTH_KEY=(실제 값)
KOROAD_BASE_URL=https://opendata.koroad.or.kr/data/rest/frequentzone

UPLOAD_DIR=/app/uploads
EOF
```

- `DATABASE_URL`은 DB가 같은 인스턴스에 있으므로 `127.0.0.1`(또는 private IP) 사용 — 굳이 퍼블릭 IP로 안 나갔다 들어올 필요 없음
- `MASKING_PYTHON`, `UPLOAD_DIR`은 컨테이너 내부 경로 기준 (Dockerfile의 `WORKDIR /app` 기준)

### 5-3. 컨테이너 실행

컨테이너가 하나뿐이라 `docker-compose` 없이 `docker run`으로 충분함 (서버에 compose 플러그인이 아예 없어서 이 방식으로 결정):

```bash
sudo docker pull choijb/public-safety-map-backend:latest

sudo docker run -d \
  --name public-safety-map-backend \
  --network host \
  --restart unless-stopped \
  --env-file ~/public_safety_map_backend/.env \
  -v ~/public_safety_map_backend/uploads:/app/uploads \
  choijb/public-safety-map-backend:latest
```

- `--network host`: 컨테이너가 호스트 네트워크를 그대로 사용 → 같은 인스턴스의 MariaDB(`127.0.0.1:3306`)에 별도 설정 없이 접근 가능
- `-v`: 업로드된 이미지가 컨테이너 재생성해도 사라지지 않도록 호스트 디렉토리에 영속화

### 5-4. 재배포 시 (코드 수정 후)

```bash
sudo docker stop public-safety-map-backend
sudo docker rm public-safety-map-backend
sudo docker pull choijb/public-safety-map-backend:latest
sudo docker run -d \
  --name public-safety-map-backend \
  --network host \
  --restart unless-stopped \
  --env-file ~/public_safety_map_backend/.env \
  -v ~/public_safety_map_backend/uploads:/app/uploads \
  choijb/public-safety-map-backend:latest
```

### 5-5. 상태 확인 명령어

```bash
sudo docker ps                                   # 컨테이너 실행 상태
sudo docker logs -f public-safety-map-backend     # 실시간 로그
curl -I http://localhost:5000                     # 로컬에서 앱 직접 응답 확인
```

## 6. nginx + HTTPS (도메인 없이 nip.io 사용)

### 6-1. 설치

```bash
sudo apt update
sudo apt install -y nginx certbot python3-certbot-nginx
```

### 6-2. 무료 도메인 대체: nip.io

도메인 없이 static IP만으로 Let's Encrypt 인증서를 받을 수 있도록, IP를 하이픈으로 바꾼 `nip.io` 주소 사용:
```
43.202.197.59  →  43-202-197-59.nip.io
```
별도 가입/설정 없이 자동으로 해당 IP를 가리킴. 실제 도메인이 생기면 나중에 교체 권장 (일부 네트워크/앱스토어에서 nip.io를 차단할 수 있음).

### 6-3. nginx 설정 (`/etc/nginx/sites-available/backend`)

```nginx
server {
    listen 80;
    server_name 43-202-197-59.nip.io;
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl;
    server_name 43-202-197-59.nip.io;

    ssl_certificate /etc/letsencrypt/live/43-202-197-59.nip.io/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/43-202-197-59.nip.io/privkey.pem;
    include /etc/letsencrypt/options-ssl-nginx.conf;
    ssl_dhparam /etc/letsencrypt/ssl-dhparams.pem;

    location / {
        proxy_pass http://localhost:5000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    }
}
```

> ⚠️ `X-Forwarded-Proto`, `X-Forwarded-For` 두 줄이 핵심입니다 (7번 이슈 참고). 이 파일을 나중에 다시 만들 일이 있으면 **이 443 블록을 절대 빠뜨리지 말 것** — 한 번 통째로 덮어쓰다가 443 블록이 날아가서 HTTPS가 끊긴 적 있음.

```bash
sudo ln -s /etc/nginx/sites-available/backend /etc/nginx/sites-enabled/
sudo rm -f /etc/nginx/sites-enabled/default
sudo nginx -t
sudo systemctl reload nginx
```

### 6-4. 인증서 발급

```bash
sudo certbot --nginx -d 43-202-197-59.nip.io
```
(도메인/IP가 바뀌면 새로 발급받아야 함)

## 7. 트러블슈팅 기록

배포 과정에서 실제로 겪은 문제와 원인, 재발 방지 포인트 정리.

| # | 증상 | 원인 | 해결 |
|---|---|---|---|
| 1 | `docker: unknown command: docker compose` | 서버 Docker에 compose 플러그인 미설치, apt 저장소에도 없음 | 컨테이너가 1개뿐이라 `docker-compose.yml` 대신 `docker run` 명령어로 직접 실행 |
| 2 | `permission denied ... docker.sock` | 사용자가 `docker` 그룹에 없음 | 명령어 앞에 `sudo`, 또는 `usermod -aG docker` 후 재접속 |
| 3 | `docker pull` 시 `not found` | 로컬에서 build/push를 아직 안 했거나 실패 | 로컬에서 `docker build` → `docker push` 먼저 수행 확인 |
| 4 | 컨테이너가 계속 재시작(crash loop), Prisma OpenSSL 에러 | `schema.prisma`에 `binaryTargets` 미지정 | `binaryTargets = ["native", "debian-openssl-3.0.x"]` 추가 후 재빌드 |
| 5 | `curl localhost:5000`이 우리 서버가 아닌 다른 응답(Werkzeug/Flask) | 예전에 띄워둔 다른 프로젝트(`my-flask`) 컨테이너가 5000번 포트를 이미 점유 | 안 쓰는 컨테이너 `docker stop`/`docker rm` |
| 6 | `pool timeout: failed to retrieve a connection ... active=0 idle=0` (DB 연결 실패) | `.env` 값에 큰따옴표(`"..."`)가 포함된 채로 `--env-file`에 전달되어 `DATABASE_URL` 파싱 실패 | `.env`에서 모든 값의 따옴표 제거 |
| 7 | 관리자 로그인은 되는데 세션 쿠키(`set-cookie`)가 안 옴 | `express-session`은 `cookie.secure: true`일 때 Express가 "진짜 HTTPS 요청"이라고 인식해야만 쿠키를 보냄. nginx가 `X-Forwarded-Proto`를 안 넘기고, Express도 `trust proxy` 설정이 없어서 항상 HTTP로 인식됨 | nginx에 `proxy_set_header X-Forwarded-Proto $scheme;` 추가 + `app.ts`에 `app.set("trust proxy", 1)` 추가 |
| 8 | cross-site(로컬 프론트 ↔ 배포 백엔드) 쿠키가 브라우저에서 저장/전송 안 됨 | `sameSite: "lax"`는 다른 origin 간 fetch/XHR 요청에는 쿠키를 안 실어줌 | HTTPS 적용 후 `secure: true, sameSite: "none"`으로 통일 (`app.ts` 세션 쿠키, `auth.controller.ts`의 `refresh_token` 쿠키 2곳) |

## 8. 코드에서 이번에 바뀐 부분 요약

- [Dockerfile](Dockerfile) — 신규 생성 (멀티스테이지)
- [.dockerignore](.dockerignore) — 신규 생성
- [prisma/schema.prisma](prisma/schema.prisma) — `binaryTargets` 추가
- [src/app.ts](src/app.ts) — `app.set("trust proxy", 1)` 추가, 세션 쿠키 `secure: true, sameSite: "none"`
- [src/controllers/auth.controller.ts](src/controllers/auth.controller.ts) — `refresh_token` 쿠키 2곳(`login`, `refresh`) `secure: true, sameSite: "none"`으로 통일
- [.env](.env) — `UPLOAD_DIR`, `MASKING_PYTHON`(컨테이너 경로), `DATABASE_URL`(private IP, 따옴표 제거) 반영 — 서버의 `.env`는 git에 안 올라가므로 서버에 직접 생성 필요

## 9. 다음에 프론트엔드까지 배포할 때 참고

- 지금은 CORS `origin`이 `"http://localhost:3000"`로 고정되어 있음 ([app.ts](src/app.ts) `cors()` 설정). 프론트가 실제 도메인으로 배포되면 배열로 바꿔서 추가해야 함:
  ```ts
  origin: ["http://localhost:3000", "https://프론트-실제-도메인"]
  ```
- 지금 쓰는 `nip.io`는 임시방편. 서비스 정식 오픈 전엔 실제 도메인 구매 + DNS 연결 + 인증서 재발급 권장
- 모바일 앱을 붙일 계획이 있다면, 지금 `refresh_token`을 `httpOnly` 쿠키로 관리하는 방식은 네이티브 앱에서 그대로 안 쓰일 수 있음 — 앱 개발 시점에 헤더 기반 토큰 전달 방식 추가 검토 필요
- `express-session`의 `MemoryStore`는 프로덕션에 부적합하다는 경고가 로그에 계속 뜸 (재시작 시 세션 전부 날아감, 메모리 누수 가능성) — 트래픽이 늘면 Redis 같은 세션 스토어로 교체 고려
