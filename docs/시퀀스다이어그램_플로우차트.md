# 시퀀스다이어그램 / 플로우차트 (v1.0)

## 1. 개요

| 항목 | 내용 |
|---|---|
| 범위 | 관리자 페이지(FN-05-01) + 유저 피드백 게시판(FN-03-01) 담당 시나리오 |
| 표기법 | Mermaid (`sequenceDiagram`, `flowchart`) — GitHub/Notion 등에서 바로 렌더링 가능 |

## 2. 로그인

이메일/비밀번호 인증 후 JWT를 발급하는 공통 흐름. 비밀번호 불일치(401)와 비활성 계정(403)을 분기 처리한다.

```mermaid
sequenceDiagram
  actor 유저
  participant 클라이언트
  participant 서버
  participant DB
  유저->>클라이언트: 이메일/비밀번호 입력
  클라이언트->>서버: POST /auth/login
  서버->>DB: SELECT user WHERE email=?
  DB-->>서버: user row (password_hash, role, is_active)
  서버->>서버: bcrypt 비교
  alt 비밀번호 불일치
    서버-->>클라이언트: 401 Unauthorized
  else 비활성 계정(is_active=N)
    서버-->>클라이언트: 403 Forbidden
  else 인증 성공
    서버->>서버: JWT 발급 (role 포함)
    서버-->>클라이언트: 200 access_token + user
    클라이언트->>클라이언트: 토큰 저장 (이후 요청 Authorization 헤더)
  end
```

## 3. 피드백 게시판 진입 (지도 버튼 경로)

지도 메인 화면에서 "피드백 게시판" 버튼을 눌러 격자 선택 모드로 전환한 뒤, 지도에서 구역을 클릭해 해당 격자의 게시판으로 진입하는 흐름 (인포카드 경유 경로와 별개의 단축 경로).

```mermaid
flowchart TD
  A["지도 메인 화면 (FN-01-01)"] --> B["'피드백 게시판' 버튼 클릭 (격자 선택 모드 전환)"]
  B --> C["지도에서 원하는 구역 클릭 (grid_id 획득)"]
  C --> D["GET /grids/id/feedbacks + /detail"]
  D --> E["SC-01 피드백 게시판 표시"]
```

## 4. 피드백 등록/수정 (중복 등록 사전 차단)

"피드백 남기기" 클릭 시, 먼저 본인 작성 여부를 확인해서 등록/수정 폼을 자동으로 분기한다. 동일 유저-동일 격자 중복 등록은 이 사전 확인으로 원천 차단하고, 409는 동시 요청 등 예외 상황의 안전장치로만 유지한다.

```mermaid
sequenceDiagram
  actor 유저
  participant 클라이언트
  participant 서버
  participant DB
  유저->>클라이언트: "피드백 남기기" 클릭
  클라이언트->>서버: GET /grids/grid_id/feedbacks/me
  서버->>DB: SELECT feedback WHERE grid_id, user_id
  DB-->>서버: 결과
  alt 기존 피드백 있음
    서버-->>클라이언트: 200 기존 데이터 반환
    클라이언트->>유저: 수정 폼 표시 (값 채움)
  else 기존 피드백 없음
    서버-->>클라이언트: 200 data null
    클라이언트->>유저: 등록 폼 표시 (빈 값)
  end
  유저->>클라이언트: 입력 후 등록/저장 클릭
  alt 신규 등록
    클라이언트->>서버: POST /grids/grid_id/feedbacks
  else 기존 수정
    클라이언트->>서버: PATCH /feedbacks/id
  end
  서버->>DB: INSERT 또는 UPDATE
  DB-->>서버: 완료
  서버-->>클라이언트: 200/201 성공
  클라이언트->>유저: 게시판 목록 갱신
```

## 5. 관리자 마커 등록 라우팅

관리자가 마커 등록 폼(SC-05)을 제출하면, 서버가 `type` 값을 판별해 제보 유형은 `report` 테이블에, 도시정보 유형은 `city_events` 테이블에 자동으로 저장한다. 관리자는 폼 하나만 사용하고 라우팅은 서버가 처리한다.

```mermaid
flowchart TD
  A["관리자: 마커 등록 폼 제출 (POST /admin/markers)"] --> B["서버: type 값 판별"]
  B --> C["제보유형 (교통사고·싱크홀·공사 등)"]
  B --> D["도시정보유형 (행사·인파밀집·교통통제)"]
  C --> E["report 테이블에 저장"]
  D --> F["city_events 테이블에 저장"]
  E --> G["지도에 즉시 반영 (앱/웹 동일 노출)"]
  F --> G
```

## 6. 관리자 삭제 (소프트 삭제)

제보/피드백 삭제는 동일한 패턴을 공유한다: 확인 모달(SC-04) → API 호출 → `is_active='N'`으로 소프트 삭제 → 목록 갱신.

```mermaid
sequenceDiagram
  actor 관리자
  participant 클라이언트
  participant 서버
  participant DB
  관리자->>클라이언트: 목록에서 삭제 아이콘 클릭
  클라이언트->>관리자: 삭제 확인 모달 표시(SC-04)
  Note over 클라이언트: 소프트 삭제 안내 문구 노출
  관리자->>클라이언트: 삭제 확인 클릭
  alt 대상이 제보
    클라이언트->>서버: DELETE /admin/reports/id
  else 대상이 피드백
    클라이언트->>서버: DELETE /admin/feedbacks/id
  end
  서버->>DB: UPDATE ... SET is_active='N' WHERE id=?
  DB-->>서버: 완료
  서버-->>클라이언트: 200 성공
  클라이언트->>관리자: 모달 닫고 목록에서 비활성 처리 반영
```

## 7. 다루지 않은 것 (분기 없는 단순 조회)

아래는 "필터 선택 → GET 호출 → 목록 표시"로 끝나는 단순 흐름이라 별도 다이어그램 없이 API명세서 참고로 충분하다고 판단했다.

- 관리자 대시보드 조회 (`GET /admin/summary`)
- 관리자 제보/피드백/도시정보 목록 + 필터 조회
