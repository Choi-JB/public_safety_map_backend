# 프로젝트 파일 구조도 (v1.0)

## 가정한 기술스택

명시적으로 정한 적이 없어 흔히 쓰는 조합으로 가정했습니다. 실제 스택이 다르면 구조를 다시 맞춰야 합니다.

| 영역 | 가정 스택 |
|---|---|
| 백엔드 | Node.js + Express, TypeScript, MariaDB, Prisma ORM (`@prisma/adapter-mariadb`) |
| 웹 | Next.js (App Router) + TypeScript + Zustand (전역 상태 관리) |
| 안드로이드 앱 | Flutter (Dart), 상태관리는 아직 미정 |

## 역할 분담 (참고)

| 역할 | 인원 | 담당 범위 |
|---|---|---|
| 공통기반 | 1명 | 인증, DB/AWS 배포, 지도·격자 기본 API (FN-01-01) |
| 지도표시팀 | 1명 | 도시정보/피난처/인포카드 (FN-01-02~04), 앱+웹 |
| 제보/알림팀 | 1명 | 제보 등록·열람·이미지 업로드·푸시알림 (FN-02-01, 01-R, 02-02), 앱+웹 |
| 피드백/관리자팀 | 2명 | 피드백 게시판(FN-03-01) + 관리자 페이지(FN-05-01) |

와이어프레임과 사용자 시나리오는 각 담당자가 자기 기능 범위 내에서 개별적으로 작성합니다.

## 참고사항

### 1. Zustand 스토어를 기능별로 쪼갠 이유

하나의 거대한 스토어 대신, **역할 분담 경계와 스토어 경계를 일치**시켰습니다.

- 지도표시팀이 `mapStore.ts`를 수정하는 동안 제보/알림팀의 `reportStore.ts`와 충돌할 일이 없음
- `authStore.ts`(로그인 상태, 토큰)는 공통기반 담당자가 만들고, 나머지 스토어들은 `authStore`의 값을 참조만 함 (예: `api/` 모듈에서 `useAuthStore.getState().token`으로 꺼내 쓰기)

### 2. Zustand 사용 시 흔한 실수

`report`/`feedback` 목록처럼 **서버 데이터를 캐싱하는 용도**로 Zustand를 쓸 때, API 재호출 시점(언제 새로고침할지)을 놓치기 쉽습니다. 예를 들어 지도를 이동했는데 `reportStore`의 목록이 갱신되지 않는 경우가 흔한 버그입니다. `mapStore`의 viewport 값이 바뀔 때마다 `reportStore`/`feedbackStore`가 새로 fetch하도록, viewport를 구독(subscribe)하는 구조를 짜두는 것을 권장합니다.

### 3. 와이어프레임 / 사용자 시나리오

팀 차원의 공용 문서로 만들지 않고, 각 담당자가 자기 기능 범위(`docs/wireframes/{기능}/`) 안에서 개별적으로 작성하는 것으로 결정했습니다. 다만 피드백/관리자팀은 여기서 한 걸음 더 나아가, 와이어프레임 외에 화면별 상세 설명(`관리자페이지_UI설계서.md`, `유저피드백게시판_UI설계서.md`)과 담당 시나리오의 흐름도(`시퀀스다이어그램_플로우차트.md`)까지 `docs/` 최상위에 별도 문서로 정리했습니다. 다른 팀도 필요하면 이 형식을 참고해 동일한 수준으로 정리하는 것을 권장합니다.

### 4. Flutter 상태관리 미정

`lib/state/`는 자리만 잡아둔 상태입니다. Provider/Riverpod/Bloc 중 무엇을 쓸지 정해지면 그에 맞는 하위 구조(예: Riverpod의 `providers/`, Bloc의 `blocs/`)로 다시 정리해야 합니다. 웹의 Zustand 스토어 분리 방식(기능별 슬라이스)과 동일한 원칙으로 가되, 실제 폴더명과 패턴은 선택한 라이브러리에 따라 달라집니다.

### 5. Next.js + Zustand 사용 시 주의사항

Next.js(App Router)는 기본적으로 서버 컴포넌트라, Zustand 훅을 쓰는 컴포넌트 파일 최상단에 `"use client"`를 꼭 붙여야 합니다. 빠뜨리면 빌드 에러 없이 조용히 상태가 안 먹히는 경우가 있어 헷갈리기 쉬운 부분입니다. `app/map/page.tsx`처럼 지도/데이터 상태를 다루는 페이지는 대부분 클라이언트 컴포넌트가 될 가능성이 높습니다.

### 6. TypeScript 타입과 API명세서 동기화

`lib/api/`에 API명세서(v1.2)의 응답 JSON 구조를 그대로 TypeScript 타입으로 옮겨서(`lib/api/types.ts` 등) 각 팀이 공용으로 import해 쓰는 걸 권장합니다. 예를 들어 `GridDetailResponse`, `ReportListItem` 같은 타입을 공통기반 담당자가 미리 만들어두면, API 응답 필드명이 나중에 바뀌었을 때 컴파일 에러로 바로 잡혀서 화면에서 값이 `undefined`로 조용히 깨지는 상황을 막을 수 있습니다.

### 7. Prisma 도입 워크플로우

이미 작성해둔 `public_safety_map_v1.1.sql`을 그대로 활용합니다.

1. `public_safety_map_v1.1.sql`을 MariaDB에 먼저 실행해 테이블/더미데이터 생성
2. `backend/`에서 `npx prisma init` 후 `.env`에 `DATABASE_URL` 설정
3. `npx prisma db pull`로 기존 테이블 구조를 `prisma/schema.prisma`에 자동 반영 (직접 손으로 옮겨 적을 필요 없음)
4. `npx prisma generate`로 타입이 포함된 Prisma Client 생성 → 이후 각 팀은 `import { PrismaClient } from '@prisma/client'`로 바로 사용
5. 이후 스키마를 변경할 일이 생기면 `schema.prisma`를 직접 고치고 `npx prisma migrate dev`로 마이그레이션 (이 작업은 공통기반 전용, 위 접근 규칙 참고)

## 폴더 접근 규칙 (코드 오너십)

각 팀은 자기 담당 폴더만 직접 수정하고, 공통 파일은 공통기반 담당자를 거치는 것을 원칙으로 합니다. 충돌을 줄이고 "누가 뭘 고쳐도 되는지" 헷갈리는 상황을 막기 위한 규칙입니다.

### backend

| 경로 | 수정 권한 | 비고 |
|---|---|---|
| `config/`, `middlewares/`, `routes/auth.routes.ts` | 공통기반 전용 | 다른 팀은 직접 수정 금지 |
| `prisma/schema.prisma` | 공통기반 전용 (최초 `db pull` 생성) | 다른 팀이 컬럼 추가가 필요하면 공통기반에게 요청 → 리뷰 후 반영 (스키마 변경은 전체 영향) |
| `routes/grid.routes.ts`, `controllers/grid.*` | 지도표시팀 전용 | |

### 공통 파일 수정이 필요할 때

담당 팀이 아닌 공통 파일(예: `config/`, `prisma/schema.prisma`, `authStore.ts`)을 고쳐야 하는 상황이 생기면:
1. 직접 수정하지 않고 공통기반 담당자에게 요청
2. 공통기반 담당자가 직접 반영하거나, 짧은 PR을 만들어 리뷰 후 병합
3. 스키마 변경(prisma/schema.prisma, DB)은 영향 범위가 크므로 반드시 이 절차를 거침

### 브랜치 규칙 (참고)

- 브랜치명: `feature/{역할}-{작업내용}` (예: `feature/map-city-events`, `feature/report-image-upload`)
- 자기 담당 폴더 밖의 파일이 diff에 포함된 PR은 병합 전 공통기반 담당자 리뷰 필수
